# 用户画像时空知识构建实施规范 v1

## 1. 适用范围

本规范用于将 `.openloom/metadata` 的文档元数据融合为用户私域画像，目标产物是 `.openloom/agent/USER.md`（混合模式：结构化 + 叙事）。

---

## 2. 元数据归一化与冲突合并规则

### 2.1 输入字段

从每个 metadata 文档中读取：

- `file_path`, `hash`, `agent_used`, `extracted_at`
- `tags.entities`
- `spatiotemporal`
- `location`
- `extraction_errors`

### 2.2 归一化流程

1. **实体标准化**
   - 人名：`Fan Yang` / `Fan YANG` / `YANG, FAN` / `杨帆` 归并为 `Fan Yang`
   - 组织名：大小写和符号归一，例如 `UTAH STATE UNIVERSITY` -> `Utah State University`
   - 地名：分拆为 `city/province_or_state/country`，无法确定则填 `Unknown` 并保留 `raw_text`

2. **时间标准化**
   - `Aug 2024 - Present` -> `start=2024-08`, `end=null`, `precision=month`
   - `Nov 2021 - May 2024` -> `start=2021-11`, `end=2024-05`, `precision=month`
   - `Unknown/Undated` -> `start=null`, `end=null`, `precision=unknown`
   - 单日时间 `2026-01-17` -> `start=end=2026-01-17`, `precision=day`

3. **事件标准化**
   - 每条事件输出统一字段：
     - `event_type`（identity/education/work/family/legal/residence/travel）
     - `statement`（统一主语时态）
     - `time`
     - `location`
     - `evidence_refs`

4. **去重合并**
   - 合并条件：
     - `event_type` 相同
     - 主体组织或核心语义一致
     - 时间区间重叠或相邻
   - 合并后保留 `evidence_refs` 并集

### 2.3 冲突识别与声明

冲突分为三类：

- **C1 时间冲突**：同一主体在同一时间区间出现互斥全职事件
- **C2 属性冲突**：同一事实字段出现不同值（如出生地、毕业年份）
- **C3 强度冲突**：单一弱证据与多源强证据相悖

冲突处理规则：

- 不直接删除冲突事件，保留为 `competing_claims`
- 对主事件打 `primary=true`，对竞争事件打 `primary=false`
- 记录 `conflict_note`，并进入 `OpenQuestions`

## 3. 置信度分层与评分机制

### 3.1 评分公式

`confidence = clamp(source_weight + agreement_bonus - conflict_penalty - extraction_penalty, 0, 1)`

### 3.2 权重定义

- `source_weight`
  - 官方证件（护照/身份证）：`0.90 ~ 1.00`
  - 简历/CV（结构清晰）：`0.70 ~ 0.90`
  - 图片语义描述（弱结构）：`0.40 ~ 0.70`
- `agreement_bonus`
  - 每增加 1 个独立一致来源：`+0.05`（最高 `+0.15`）
- `conflict_penalty`
  - 轻微冲突：`-0.10`
  - 明显冲突：`-0.25`
  - 严重冲突：`-0.40`
- `extraction_penalty`
  - 存在提取错误：`-0.10 ~ -0.30`

### 3.3 置信度分层

- `high`：`>= 0.85`（可作为稳定事实）
- `medium`：`0.60 ~ 0.84`（可进入画像，但需标注）
- `low`：`< 0.60`（仅作为线索，不写成确定结论）

## 4. 敏感信息存储与访问规范（单文件策略）

### 4.1 总体策略

- 不新增 `USER.redacted.md`，仅保留单一主文件：`.openloom/agent/USER.md`。
- 敏感信息允许在 `USER.md` 明文存储，以保证本地 LLM 读取与推理完整性。
- 访问控制在程序层实现，避免直接暴露文件原文。

### 4.2 敏感字段目录

- 证件号（护照、身份证、驾驶证）
- 精确地址（门牌级）
- 电话、邮箱
- 法律文书编号
- 证件完整有效期细节

### 4.3 运行时安全护栏

- 程序日志默认脱敏，禁止打印完整 `USER.md`。
- 非本地受信路径禁止直接读取 `USER.md` 原文。
- 对外接口不得回传原始敏感字段，必须经过显式导出策略。
- 导出/分享动作默认拒绝，需显式确认并记录审计日志。

### 4.4 失败回退

- 若访问控制模块异常：拒绝访问 `USER.md` 原文并记录错误。
- 若导出策略模块异常：默认拒绝导出，保留本地内容不变。

## 5. 可追溯叙事模板

### 5.1 段落结构

- `General`
- `Study`
- `Work`
- `Family`
- `ResidenceAndMobility`

### 5.2 叙事写作规则

- 每段最多 3 句，按时间顺序
- 每句至少包含两个维度：`时间/地点/事件` 之一
- 段尾必须附 `evidence_refs: [...]`
- 遇到低置信信息必须使用保守措辞：
  - `signals indicate ...`
  - `possible ...`
  - `requires stronger evidence`

## 6. 验收检查清单（Definition of Done）

### 6.1 一致性检查

- [ ] 同一时间段不存在未声明的互斥全职事件
- [ ] 时间格式统一（YYYY-MM 或 YYYY-MM-DD 或 null）
- [ ] 每条事件有稳定 `event_id`

### 6.2 可追溯性检查

- [ ] 每条结构化事件至少 1 个 `evidence_ref`
- [ ] 每段叙事附有 `evidence_refs`
- [ ] `evidence_index` 能反查到 `source_hash` 与 `source_file`
- [ ] 事实级证据引用与全局 `EvidenceIndex` 双向一致

### 6.3 隐私检查

- [ ] `USER.md` 原文不通过外部接口直接暴露
- [ ] 程序日志不打印敏感字段明文
- [ ] 导出路径默认拒绝并带显式审计

### 6.4 可读性检查

- [ ] 2 分钟内可读懂核心人生轨迹
- [ ] 关键轨迹覆盖教育、职业、居住
- [ ] 家庭相关仅在证据足够时进入确定陈述

---

## 7. 增量更新建议

- 新 metadata 到达时执行：
  1. 归一化
  2. 合并与冲突重评分
  3. 更新 timeline
  4. 更新叙事
  5. 运行验收清单
- 每次更新都保留旧版本快照，便于审计与回滚。
